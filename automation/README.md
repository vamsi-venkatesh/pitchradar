# Automation boundary

PitchRadar's whole operating cycle is a single idempotent command — `npm run cycle:scheduled`, guarded by a PostgreSQL advisory lock so two overlapping runs cannot both collect — and *what* invokes it on a schedule is deployment-specific: timer units, workflow runner, credentials, destinations and message templates all live with the deployment, not with the engineering core, so none of them are published here. The boundary that matters is in the code, not the scheduler: no outbound connector is implemented. An approved action reaches the state `approved_waiting_connector` and stops there; organizer email, application submission and WhatsApp delivery would each need a connector that is separately built, secured and audited before anything leaves the system.
